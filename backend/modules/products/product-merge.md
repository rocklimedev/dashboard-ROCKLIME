In Inventory, select exactly two rows and click Merge two products. Users need both edit and delete permission in products/inventory; SUPER_ADMIN and DEVELOPER also have access. Choose which product to keep, review the live preview and differences, choose final stock and selling price, then confirm that these records represent the same product.

Stock defaults to keeping the surviving product's stock, to avoid double-counting copied duplicate quantities. Alternatives are sum, source stock or an explicit final quantity. Price can remain the keeper's, use the source's, or be entered explicitly (including zero). The keeper's UUID, internal product code, name, status, relationships and conflicting metadata are retained. Missing metadata is filled, images are deduplicated and keywords are unioned. Source metadata and both original product records are retained in the audit snapshot.

Products must share one unambiguous company code and the same brand. Masters owning variants, different parents or different variant fields block the merge. Similar names alone do not establish that a merge is appropriate; review metadata differences such as size or color.

Supported MySQL productId references and exact product identifiers in JSON records are transferred inside the same database transaction as stock, metadata, keywords, the merge history record, the activity audit and source deletion. Historical names, prices and totals are not recalculated. Inventory history keeps its original timestamp, actor, quantity change and original resulting quantity; a provenance note identifies the original source product. These imported balances describe the source's original history, not a retroactively recalculated consolidated ledger. The merge correction records the chosen final stock. ActivityLog/OrderActivity audit snapshots are preserved.

MongoDB records are checked but are not rewritten. If the product being removed is referenced in carts, order items, quotation items/versions, purchase order items or FGS items, the preview blocks the merge. Keep the referenced product if the other record is unused; if both are referenced, resolve their references before merging. Documents containing both selected products also block the merge, because replacing IDs could create ambiguous duplicate lines. Cross-database reference checks cannot provide a distributed lock against simultaneous MongoDB writes; perform merges while these products are not being added to sales documents. MongoDB must be available for the checks to complete.

POST /api/products/inventory-bulk/merge-preview accepts { keeperId, sourceId } and returns full product snapshots, field differences, reference counts, blockers and a fingerprint. POST /merge accepts { keeperId, sourceId, fingerprint, stockMode: keep|sum|source|custom, priceMode: keep|source|custom, quantity?, sellingPrice?, note? }. The server rechecks permissions, locks products in UUID order, rechecks references and validates the fingerprint. Changed products/references return 409. Foreign keys remain enabled; an unexpected constraint or failed history/audit write rolls back all MySQL changes. A repeated confirmation after success finds the source missing and cannot transfer its stock twice.

The preview JSON can be downloaded before confirming. The PRODUCTS_MERGED activity log records before/after snapshots, actor, choices and moved record IDs. There is no automatic undo endpoint.

Run npm run products:merge:test and npm run inventory:bulk:test from backend. Merge tests use an in-memory SQLite database with foreign keys and real transactions; they do not modify the configured production database.
